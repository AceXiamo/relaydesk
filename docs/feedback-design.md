# Feedback Portal, Widget & Triage Agent Design Reference

This document records the external interaction, motion, and visual-system references inspected during the RD-21 feedback experience rework, together with the concrete design decisions adopted in Relaydesk (`app/`, `public/widget.js`, `server/feedback-agent.ts`).

## Sources Inspected

All references below were reviewed directly in-browser via DesignBookmark:

- **DesignBookmark Motion** — `https://designbookmark.com/motion` (All & AI categories, including live DesignBookmark components and curated Kokonut UI / SmoothUI entries)
- **DesignBookmark Design Directory** — `https://designbookmark.com/design`
- **DesignBookmark Design Systems** — `https://designbookmark.com/design/design-systems`

## Runtime Architecture & Safety Guardrails

1. **Local Bridge Read-Only Sandbox**: Feedback diagnosis runs directly on the user's connected Local Bridge computer using the native read-only sandbox (`sandbox_mode: "read-only"`, `network_access: false`) with no file writes, no internet access, and no database or ops MCP credentials injected.
2. **Code & Screenshot Inspection without Leakage**: Within the read-only sandbox, the agent may inspect the bound project repository and user-uploaded screenshots to distinguish usage questions from real defects, while system instructions strictly prohibit exposing raw source code, internal file paths, tokens, or infrastructure details.
3. **Honest Offline Policy**: There is no cloud-key fallback. If the configured Local Bridge node is offline (`agent_available: false`), `/diagnose` rejects requests with HTTP `503` and both Portal and Widget explicitly report that the diagnosis assistant is offline and not accepting online diagnosis.
4. **Zero-Ticket Resolution for Usage Questions**: Conversations classified as `clarify` or `usage` never create tickets. Only `suspected_bug` produces a draft card, and a task is created only upon explicit user confirmation.
