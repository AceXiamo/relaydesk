# Relaydesk 项目交接

首版实现基线为 `53bb13e`。Relaydesk 面向维护多个应用的开发者。每个应用引入一个反馈组件，使用者在遇到问题的地方描述需求；维护者在独立工作台中整理反馈、确认要求、指定负责人。开发机上的 coding agent 从对应项目的队列领活。

## 从对话面板到项目队列

最初讨论的是把对话面板放进应用，帮助用户把「这里有问题」讲清楚。一个典型例子是订单页筛出 23 条、勾选了 5 条，用户说「导出错了」。页面上的数字无法说明用户意图；追问才知道用户想导出 23 条，而勾选是为了稍后发货。这个例子解释了为什么要同时保留**反馈原话**和**确认后的执行要求**。数字来自讨论示例，现有组件通过用户输入收集上下文，页面地址由用户选择附上。

随后确定了三个直接影响实现的产品决策。

| 用户需要 | 首版的处理方式 |
| --- | --- |
| 应用和群聊都能收问题，开发机离线也能用 | 收集端按项目写入持久化队列。工作台也可手动录入。首个群平台选用 Telegram。 |
| 我能挑一条自己做，也能接过 agent 正在做的活 | 状态与负责人独立存储。人工认领、请求交接、撤销旧执行器的写回权分别有明确操作。 |
| 我想针对某条反馈继续聊，几个人也可能报同一个问题 | 每单拥有讨论串。维护者显式保存执行要求，可以把重复反馈并入主单，仍能回查各自的原话、来源和讨论。 |

## 一条反馈如何走到验收

1. **绑定项目。** 维护者在面板设置 GitHub 仓库和项目级 Agent 指令。应用页面复用该项目的嵌入片段。项目的组件、bot 和执行器各有独立凭据。
2. **收集与澄清。** 组件提供一次可跳过的追问，用户预览并确认后提交。Telegram 监听指定群里的显式 `/feedback` 命令，支持引用原消息。服务端根据项目、来源和外部标识去重，新单进入 `triage`。任务讨论默认用本地规则，也能接兼容 Chat Completions 的模型。[收集端接入](../integrations/README.md) · [助手配置](assistant.md)
3. **决定谁做。** 原话、讨论串和执行要求各自保存。维护者可写下「导出全部筛选结果，勾选状态不影响导出范围」，再将任务设为 `ready`。点击「我来处理」只改变归属，所以「待处理 · 我」是有效组合。
4. **本机执行。** 执行器校验本地 Git origin 与项目绑定，在 SQLite 写事务里由服务端分配任务。执行器在独立 worktree 中运行本地配置的命令，输入包括项目指令、反馈、合并的原话和确认后的要求。开发者在本机决定命令、账号和沙箱权限。[执行器说明](../agent/README.md)
5. **验收。** 命令成功退出后，执行器把分支、HEAD 和变更数量写回，任务进入 `review`。维护者可检查现场、验收、提交和合并。把 Relaydesk 首版源码推到私有 GitHub 仓库，是这次交付操作；任务执行器本身只负责本地执行和回报。

## 改队列前先看这几种竞态

`status` 使用 `triage / ready / working / handoff / waiting / review / done`，`owner` 使用 `none / human / agent`。以下是典型操作的结果，维护者也能在面板上重新整理任务状态。

| 场景 | 服务端与执行器的约定 |
| --- | --- |
| 多个执行器同时领活，或者你也点了认领 | 领取条件是本项目中 `ready + none` 且尚未并入主单。挑选和改写归属在同一个事务中完成，按优先级、再按任务编号领取。每次成功领取都会签发独立的 lease。 |
| agent 工作时，你补充一条讨论 | 讨论记录可以更新，执行版本保持有效。显式保存新要求会增加任务版本；旧版本提交完成结果时会被拒绝。执行器检测到变更后暂停并回报待补充。 |
| 你请求接手 | 先进入 `handoff + agent`。执行器在心跳时发现请求，停止前台命令所在的进程组、保留工作树并回报；确认后变为 `working + human`。 |
| 执行器掉线，你强制接手 | 服务端撤销 lease，拒绝旧执行器后续写回。离线机器上的进程何时停止，仍取决于本地停止或恢复同步。可根据最后同步时间、分支和 worktree 找回现场。 |
| 命令结束后回报失败，或执行器意外退出 | 执行器将活动任务和待回报结果记在本机。使用相同配置重启会重试回报；上次执行中断时保留现场，转待补充供人工核对。 |

## 本地复核与部署上下文

在仓库根目录运行 `python3 server.py`，打开 <http://127.0.0.1:8787>。复核认领逻辑时，可创建一条「待处理」任务，先点「我来处理」，再让执行器轮询一次；释放认领后再次轮询，任务应由 agent 领取。在长任务中请求接手，可以观察交接记录和保留下来的工作树。启动参数、远程面板认证和 SQLite 持久化见 [README](../README.md)。

```sh
python3 -m unittest discover -s tests -v
node --check public/app.js
node --check public/widget.js
```

首版交付时通过了 17 项自动测试，并用真实 HTTP 和临时 Git 仓库验证了本地命令从领取到待验收的流程。执行测试使用替代命令；接手者自己的 coding agent、模型服务和 Telegram 实群需要相应配置后联调。面板交互经过 DOM 与 HTTP 联调，浏览器视觉验收仍待完成。
